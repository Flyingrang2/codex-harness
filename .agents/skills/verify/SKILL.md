# verify — 「완료」 메시지 ≠ 완료

사용자가 눈으로 직접 확인할 수 있는 증거를 만들어. 틀린 게 보이면 **고치지 말고 먼저 보고해**.
「끝났다」는 말은 방금 새로 돌린 명령의 출력으로만 해. 네가 낸 결과도, 다른 에이전트가 「성공」이라고 한 말도 그대로 믿지 마.

## 하지 말 것
- 테스트를 통과시키려고 기대값을 바꾸지 마
- 필드 이름·타입·순서 같은 출력 형식을 바꾸지 마
- 검증 결과를 좋게 포장하지 마 — 실패는 실패라고 써
- 없는 숫자를 지어내지 마 — 고치기 전 값을 안 재 뒀으면 「기록에 없음」이라고 써

## 순서
0. **고치기 전 기준값**: 고치기 전이라면 지금 돌린 명령과 결과, 핵심 숫자를 먼저 적어 둬.
1. **전후 비교**: 고치기 전과 후에 같은 명령을 돌려 나온 핵심 숫자를 표로 비교해. 바뀐 칸만 표시하면 돼. 데이터를 남기거나 빼거나 고치거나 미룬 기준별로 몇 건인지, 처리 전후 행 수가 얼마인지 적어. 여러 기준에 겹치는 행이 있으면 겹친다고 밝혀.
2. **독립 재계산**: 핵심 숫자 1~2개를 골라 **원본 행부터 다른 방법**으로 다시 계산해서 값이 같은지 봐. 다른 코드로 돌리거나, 짧은 일회용 명령을 쓰거나, 손으로 계산할 수 있는 작은 표본을 쓰면 돼.
   - 핵심 숫자가 결과를 좌우하면 서브에이전트를 하나 띄워 원본 파일과 질문만 주고 따로 계산시켜서 비교해. 우리 결과나 정답은 알려 주지 마. 서브에이전트를 못 띄우면 다른 코드로 직접 다시 계산해.
   - 이 방법은 계산이 맞는지만 봐 줄 뿐, 무엇을 빼고 넣을지 정한 기준 자체는 확인하지 못한다고 함께 밝혀.
3. **경계·반례 3개**: 빈값을 넣었을 때, 기간 끝·0·동점처럼 경계에 걸릴 때, 빼기로 한 행이 정말 빠졌는지 확인해.
4. **요구사항 대조**: README와 담당자 기준을 하나씩 지켰는지 ✅/❌로 표시해. 파일과 줄 번호나 실행 결과로 근거도 달아.
5. **테스트**: 돌린 명령과 통과·실패 개수를 그대로 보여 줘.
6. **형식**: 출력 파일이나 API 응답 필드가 처음 요구한 그대로인지 확인해.
7. **검산 남기기**: 2단계에서 확인한 핵심 숫자를 테스트 1개로 남겨서 다음 단계마다 다시 돌려. 새 파일을 만들 땐 먼저 허락받고. 같은 실수가 또 나오면 바로 잡을 수 있게 해 둬.

## 보고
- 맨 위 한 줄에 「검증 통과」 또는 「문제 N개 발견」이라고 써.
- 문제마다 무엇이 잘못됐는지, 어떤 명령과 숫자로 알았는지, 어떤 영향이 있는지, 어떻게 고칠지 제안해. 아직 직접 고치진 마.
- 네가 짠 코드나 네 판단 때문에 생긴 문제면 그렇다고 솔직하게 밝혀. 사용자가 NOTES.md 「## AI 오답노트」에 적을 수 있게 해.
